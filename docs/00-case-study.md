# Slotly — кейс системного аналитика

## Контекст

Небольшая студия принимает записи через администратора и таблицу. Пока администратор проверяет свободное время и отвечает одному клиенту, тот же интервал может запросить другой. Цель MVP — дать клиенту самостоятельную запись, сохранив единственный источник правды о расписании и исключив двойное бронирование.

Это учебный аналитический кейс: сервер не развёрнут, а бизнес-метрики станут предметом пилота. Все проектные допущения, границы и открытые вопросы зафиксированы в [контексте](01-business-context.md).

## Ключевой риск и решение

**Риск:** два клиента почти одновременно создают запись на один свободный слот.

**Почему недостаточно проверить доступность на клиенте или перед INSERT:** между чтением и записью состояние может измениться. Поэтому ответ о доступности в списке слотов — лишь снимок, а окончательное решение принимается в транзакции.

**Решение:**

1. API сериализует повторные запросы одного клиента с одним `Idempotency-Key`.
2. В транзакции блокируется слот, затем повторно проверяются его состояние, услуга и время.
3. PostgreSQL сохраняет последнюю гарантию: частичный `UNIQUE` не позволяет двум `CONFIRMED` ссылаться на один слот.
4. Успешный повтор с тем же ключом возвращает исходный `201`; другой слот с тем же ключом возвращает `409`.

Подробный алгоритм и конкурентная sequence-диаграмма: [Процессы и UML](04-processes-and-uml.md). Альтернативы фиксированных слотов — в [ADR-001](../decisions/001-fixed-slots.md), политика ключа — в [ADR-002](../decisions/002-idempotency-result.md).

## Проверяемость

Решение не заканчивается на схеме API. Для каждой критичной бизнес-цели определены правила, контракт, ограничение данных и приёмочные проверки. Быстрый обзор — в [матрице трассировки](08-traceability-matrix.md); полный набор тестов — в [приёмке](07-acceptance.md).

| Сценарий | Ожидаемый результат |
|---|---|
| 50 параллельных запросов на слот | один `201`, остальные `409`, в БД одна активная запись |
| Клиент не получил ответ и повторил запрос с тем же ключом | исходный `201` и то же тело; дубликат не создаётся |
| Ключ повторно применён к другому слоту | `409 IDEMPOTENCY_KEY_REUSED`; второй слот остаётся свободным |
| Запись отменена | история сохраняется; слот снова доступен для новой записи |
