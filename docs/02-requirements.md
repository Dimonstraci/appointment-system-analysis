# 02. Требования

Требования определяют объём MVP. Must — обязательное условие его приёмки. Авторизация проверяется на сервере.

## Функциональные требования

| ID | Приоритет | Требование | Критерий |
|---|---|---|---|
| FR-01 | Must | Гость и клиент получают активные услуги с ID, названием и длительностью | Неактивные услуги не возвращаются; пустой каталог → 200 и [] |
| FR-02 | Must | По услуге и дате система возвращает доступные слоты | Исключены занятые, неопубликованные и уже начавшиеся; сортировка startsAt, id |
| FR-03 | Must | Клиент создаёт запись на доступный слот | 201 с ID; второй конкурентный клиент получает 409 SLOT_UNAVAILABLE |
| FR-04 | Must | Клиент читает только свою запись по ID | Чужой и несуществующий ID дают одинаковый 404 |
| FR-05 | Must | Клиент отменяет свою запись не позднее чем за 2 часа | Ровно 2 часа — 200; меньше — 409 CANCELLATION_WINDOW_CLOSED |
| FR-06 | Must | Администратор получает записи на дату слота | Все статусы, сортировка startsAt, id; клиент → 403 |
| FR-07 | Must | Администратор отменяет любую активную запись строго до начала | После начала → 409 CANCELLATION_WINDOW_CLOSED; причина обязательна |
| FR-08 | Must | Успешное создание защищено от повторов | Один ключ и тот же slotId → исходный 201 и тело; другой slotId → 409 IDEMPOTENCY_KEY_REUSED |
| FR-09 | Must | Система сохраняет время и инициатора создания и отмены | История отмены остаётся после новой записи на освободившийся слот |

## Бизнес-правила

| ID | Правило |
|---|---|
| BR-01 | Не более одной записи CONFIRMED на слот; ограничение обеспечивает БД |
| BR-02 | Слоты одного специалиста не пересекаются; интервалы полуоткрытые [начало, конец), соседние допустимы |
| BR-03 | Клиент — субъект проверенного токена, а не clientId из запроса |
| BR-04 | Дата поиска — локальная дата студии. Разрешены сегодня и 29 следующих дат. При создании повторяется та же проверка |
| BR-05 | Время передаётся RFC 3339 с offset, хранится как timestamptz, сравнивается по серверным часам |
| BR-06 | Отмена переводит CONFIRMED → CANCELLED. Обратный переход отсутствует. Новая запись получает новый ID |
| BR-07 | Повтор отмены уже отменённой записи возвращает 200 и её текущее состояние без изменения исходной причины и автора, даже после начала слота |
| BR-08 | Длительность слота равна длительности услуги; импорт проверяет это до публикации |
| BR-09 | Закрытие окна самоотмены не отменяет запись автоматически |
| BR-10 | Совпадающие записи у одного клиента к разным специалистам не запрещены в MVP; это открытый продуктовый вопрос |

## Матрица доступа

| Операция | Гость | Клиент | Администратор |
|---|---|---|---|
| Каталог и слоты | Да | Да | Да |
| Создать запись | Нет | За себя | Нет |
| Получить запись по ID | Нет | Свою | Любую |
| Отменить | Нет | Свою, ≥ 2 ч | Любую, до начала |
| Получить список на дату | Нет | Нет | Да |

## Нефункциональные требования

| ID | Требование | Метод приёмки |
|---|---|---|
| NFR-01 | p95 GET ≤ 500 мс, POST ≤ 800 мс при 20 RPS в течение 10 минут, 10 000 слотов и 5 000 записей | Нагрузочный тест на согласованном стенде; исключить время IdP; считать от входа до выхода API |
| NFR-02 | 0 двойных активных записей при 50 одновременных запросах на слот | Конкурентный тест + SQL-аудит; ровно один 201 для разных клиентов/ключей |
| NFR-03 | Все защищённые маршруты проверяют токен и права на объект | Негативные тесты: нет токена, токен истёк, чужая запись, роль client на admin |
| NFR-04 | Ответ после commit; при сбое до commit запись и ключ не сохраняются частично | Инъекция сбоя перед commit и повтор с тем же ключом |
| NFR-05 | В журналах API нет токенов и текста причины отмены; каждому запросу присваивается requestId | Проверка логов на наборе запросов; requestId присутствует в ошибке |
| NFR-06 | Ошибка интерфейса сохраняет выбор услуги/даты; при 409 предлагает обновить слоты | Ручной UX-тест конкурентной записи |

Числа NFR-01 — согласуемые цели, не результаты испытаний. SLA доступности, RPO/RTO и срок хранения данных требуют входных данных от владельца.
