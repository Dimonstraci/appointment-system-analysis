# ADR-002. Повтор успешного создания по ключу идемпотентности

**Статус:** принято в спецификации MVP. **Дата:** 2026-09-07.

## Контекст

Клиент может не получить ответ после того, как сервер уже создал запись: сеть оборвалась, приложение закрылось или истёк клиентский таймаут. Обычный повтор `POST /appointments` способен создать вторую запись или вернуть конфликт, хотя пользователь ожидает узнать результат первой попытки.

Ключ идемпотентности приходит в заголовке `Idempotency-Key`. Его область — пара `(clientId, key)`: ключ одного клиента не влияет на другого.

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Не хранить результат | Простая схема | Повтор после потери ответа неотличим от новой команды |
| Хранить все ответы, включая ошибки | Полная история | Временная ошибка или конфликт навсегда блокируют допустимый повтор |
| Хранить только успешный результат ограниченное время | Повтор безопасен; временная неудача может быть повторена | Нужно явно сообщить TTL и семантику после отмены |

## Решение

Выбран третий вариант:

- только успешный `201` сохраняется вместе с исходным телом ответа на 24 часа;
- повтор с тем же ключом и тем же `slotId` возвращает исходные статус и тело, даже если запись позже отменена;
- тот же ключ с другим `slotId` до истечения TTL возвращает `409 IDEMPOTENCY_KEY_REUSED`;
- неуспешные ответы не кэшируются: после исправления входных данных или освобождения слота клиент может отправить новую команду;
- результат с истёкшим TTL удаляется в транзакции, после чего ключ можно использовать снова.

## Последствия

API документирует, что повтор команды восстанавливает *результат исходной команды*, а не текущее состояние записи. Актуальное состояние клиент получает через `GET /appointments/{id}`. Это устраняет неоднозначность после отмены и позволяет безопасно повторять запрос при неизвестном результате.

В реализацию необходимо включить атомарное сохранение записи и результата ключа в одной транзакции. Для двух одновременных запросов с одинаковой парой `(clientId, key)` нужна сериализация до чтения сохранённого результата. Подробный алгоритм приведён в [процессах](../docs/04-processes-and-uml.md); ожидаемые сценарии — TC-05, TC-06, TC-21, TC-25 и TC-26.
